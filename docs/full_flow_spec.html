1. 統一輸入 bundle

先前的問題:「輸入」在每個資料源都是不同格式 —— OHLCV 有 --input-json, funding/OI 是 --derivatives-dir 底下的 parquet,Square 新聞根本沒有檔案格式 (只有 live API),內網 BigData 又是自己的 client。 想同時吃價格 + funding + 新聞的策略無法用一個檔案餵, 也就意味著一次執行無法重現、無法版控、無法 diff、無法交給別人。

1.3 回看窗格 — 為什麼一個決策不是 1.7 MB

第一版做錯了:K 線有 max_bars 上限, metric frame 卻完全沒有上限。結果一個 1 小時的決策把 30 天的 5 分鐘未平倉量整段拖進來 —— open_interest 一個 frame 12,144 列,佔掉 1.7 MB 檔案的 94%,而那些資料沒有任何策略會讀。

bundle 是一個決策時點的輸入,所以每個序列只需要一個回看窗格,不是全部歷史。 _tail_per_series() 對每個 (instrument_id, metric) 只留最新 N 筆:

策略輸出完全沒變 —— 同樣 open_long、 同樣 score=45.0、同樣 4 個 reason_codes、evidence 數值一模一樣。

build_input_bundle(
    ...,
    max_bars=300,            # K 線:最多 300 根
    metric_lookback=240,     # 每個 (instrument, metric) 最新 240 筆(預設)
    max_event_rows=200,      # 事件 / 排名類 frame 上限(預設)
)
# 要全量歷史就傳 None —— 但那是明確的選擇,不是預設

沒修的第二個成本:長表每列都重複欄位名 —— 一列 MetricFrame 約 136 bytes,其中 63 bytes(46%)是欄位名。 這是「一套詞彙」換來的代價:因為每列自帶完整標籤,funding / OI / 內網 metric 才能用 同一個 accessor 讀。改欄式編碼可再省約 46%,但會失去「一列就是一筆、可讀」的特性, 現在 159 KB 還不值得付這個代價。

1.4 兩個讓它值得存在的不變量

① 一個時鐘。每一列在寫出前都過 available_time <= decision_time。 available_time 是「我們最早何時可能知道這一列」,不是「事情何時發生」—— 把兩者混為一談,就是 walk-forward 悄悄讀到未來的方式。只 gate 一次、在建 bundle 時, 下游任何讀取者都不可能弄錯。
② 一套詞彙。funding、OI、清算、任何內網 metric 全部落成 MetricFrame (instrument_id / metric / value / event_time / available_time)。 一支讀三種的策略用同一組欄位名,而新增一個資料源不需要任何新管線 —— 它就是多幾列 MetricFrame。

1.5 內網資料:欄位在公開 repo,client 不在

約束:內網 BigData 節點(indicators API / futuresRadar / 熱點事件 / 事件曆 / 代幣解鎖 / 總經 / ETF 流向 / 板塊輪動 / 大額進出金…)是策略真的要用的輸入, 但它們的 client 不能進這個 repo —— 它硬編內網主機名,而本 repo 是 PUBLIC。那些主機名連在註解裡都不寫,寫下來就等於發布。

data/internal_slots.py 把兩者拆開:欄位契約留在公開 repo,fetcher 只用字串路徑引用。 這個模組不 import 任何內網套件;沒裝時每個插槽回報 unavailable, 而 bundle 的結構完全不變。已宣告 12 個插槽:

1.7 catalog:哪些資料能拿來回測

data/catalog.py 收錄 66 個資料節點,每個都標明可回測性:

{
 "BACKTESTABLE": 6,
 "FORWARD_ONLY": 30,
 "SEMI": 21,
 "EXTERNAL_PENDING": 9
}
只有 6 個節點是 BACKTESTABLE。 30 個是 FORWARD_ONLY —— Redis-TTL 快照, 沒有時點歷史,拿去 walk-forward 會在每一根重複使用「今天的值」。 catalog 用 pit_hazard 欄位逐一寫明它「會怎麼騙你」。 「有這個資料」不等於「能拿來回測」。

1b. 同一個 envelope,live 取數版

上面那份 bundle 是讀本機檔案組出來的。實盤要的是直接打 API —— cyqnt_trd/standard_bot/data/live_bundle.py 的 build_live_bundle() 做這件事,吐出完全相同的 envelope, 所以 paper / live 產訊號讀到的檔案形狀跟回放一模一樣。

先前的問題:catalog 宣告的參數名和實際 fetcher 收的參數名不一致, 而 runtime/data.py 會把宣告的預設值自動塞進去 —— 所以 data.klines(symbol=…, interval=…, limit=…) 不管怎麼呼叫都會 TypeError。25 個可呼叫節點裡 8 個是這樣, 包含 klines 這個最基礎的節點。既有測試全綠,因為它只驗 fetcher import 得到,沒驗呼叫得動。

修法是在節點上宣告 param_aliases 做邊界翻譯 —— 對外保留 market_type(那是 DATA_API.md 與 spec 的契約), 對內轉成 fetcher 要的 market。護欄在 tests/standard_bot/test_node_params_match_fetchers.py: 宣告的參數必須是 fetcher 簽名的子集。

2b. blocks 的輸入格式 — to_panel()

· oi_change_pct(frame) → TypeError;
· oi_change_pct(frame["value"]) → 不報錯,但值是錯的 —— 那一欄把 oi_base 和 oi_value 交錯放在一起, 算出來是「跨兩個不同指標的變化率」。第二種是危險的那種, 而且呼叫端再小心也防不了。

2b.2 三個關鍵設計決定

  1. 對齊用 available_time,不用 event_time。 一根 bar 只能看到它收盤時已經可知的值。event_time 是事情 發生的時間,可能早於可發布時間 —— 用它對齊就是前視。
  2. 最後一根 bar 的截止點是 decision_time,不是 bar 收盤。 那一列就是「現在要下的決策」:實盤 bot 在 bar 收完後決策時,確實知道當下的 24h ticker / 盤口 / 社群熱度,而這些的時間戳都晚於收盤。若最後一列也用收盤截, 所有快照類來源會全部是 NaN —— 看起來嚴謹,但唯一有用的那一列變成空的。 前面每一根仍用自己的收盤截,所以回放是誠實的。
  3. 撞名帶節點名。long_short_ratio 和 top_trader_ratio 都產出一個叫 long_short_ratio 的 metric,但量的是不同族群(全部帳戶 vs 頂級交易者)。所以第二個叫 top_trader_ratio.long_short_ratio,而不是 long_short_ratio_2。

多標的:to_panel(bundle, symbols=[...]) 回 (symbol, 欄位) 的 MultiIndex,供選幣 / 截面策略用; panel["BTCUSDT"] 切回單標的就是 blocks 吃的那張表。 防前視的測試在 tests/standard_bot/test_panel.py。

4.1 為什麼是 v2 而不是 v1

v1(signal.schema.json)v2
部位指令 side ∈ long|short|flat × action ∈ entry|exit|adjust —— 兩個欄位的組合,而且沒有任何驗證。side=flat, action=entry 這種無意義組合照樣通過;加倉與開倉都是 long/entry、 減倉與全平都是 long/exit,分不出來;反手要拆成兩筆 一個封閉列舉 intent(12 值)+ 框架自動導出 target_side / closes_side / order_side / reduce_only,消費端不需要自己組合推理
誰能發平倉無限制 沒宣告 reads_positions=True 的 bot 發 close/reduce/flip 會被 decide_checked() 丟 CapabilityError —— 沒看過部位就不能斷言部位存在
出場stop_loss + take_profit[] 兩個裸欄位, 沒有 trailing / time_stop ExitPlan:stop / TP 階梯 / trailing / time_stop,隨訊號走
型別判斷kind ∈ trade|selection|alert|noop 同一個 kind(v2 第一版漏了,已補回;而且改為推導而非宣告)
三種 bottrade / selection 各自一組欄位,以註解分段 三者同一組 key,靠 kind 分流
產出者每支策略手寫 generate()框架產生

v1 唯一勝過 v2 第一版的地方就是 kind。把交易與選幣放進同一個 envelope,前提是有一個欄位說得出「這是哪一種」—— 那個欄位不該靠推論。

4.2 v2 → 既有引擎的橋接

原本 v2 bot 跑不了回測:runner.py 做 float(payload["size"]) —— v2 的 size 是 SizeSpec 物件 → TypeError; 它讀 payload["exit_spec"],v2 叫 exit_plan → 停損被靜默忽略。

在傳輸邊界加轉譯(不動引擎),v2 dict 原封保留,額外附上引擎要的 key:

{

 "engine_size": 0.8242848612538045,

  "max_bars": 48,
  "side": "long",
  "atr_at_entry": 454.85428354185905,

engine_size 刻意不叫 size —— 覆寫掉會讓 payload 失去自身 schema 合規性。此處 RISK_PCT 1% ÷ 停損距離 = 0.8242848612538045。

三個「拒絕猜測」的決定

  1. QUANTITY / QUOTE_AMOUNT / POSITION_PCT 不換算 —— 需要帳戶權益或現有部位。引擎預設是 1.0(滿倉),猜錯就是靜默滿倉, 所以設 engine_size=null + size_unresolved 說明。
  2. RISK_PCT 只在停損距離可解時換算(上限 1.0)。
  3. 分批止盈只保留第一段並記錄 _dropped_tp_legs —— 沒有任何模擬引擎支援 partial close,靜默截斷比直說更糟。

5.1 輸入 schema 原本驗不到任何東西

同一個 cyqnt.input/v1 有三種方言。 input_bundle_example.json 用 frames[node] = {shape, rows}、 整數 ms;bot_context.json 把 rows 包在另一種 key 的外殼裡、用 ISO 字串; 而 schema 自己描述的是第三種(typed 底下的裸陣列)。 三者都宣告自己是 cyqnt.input/v1。

更糟的是 frames 當時是 additionalProperties: true, 而每個真實產出者寫的都是 frames 不是 typed —— 七個 shape 定義從來沒有被執行過。把 K 線那格塞成 [{"close": "not-a-number"}] 仍然驗過。

現在 schema 描述外殼,並用 if shape == "BarFrame@1.0" then rows: [...] 把 rows 綁到它宣告的 shape 上。外殼不是包裝:status / reason 是「沒讀到」和「讀了是空的」唯一分得開的地方,source_fallback 讓「這次是換來源拿的」看得見。四份 artifact 現在同一個形狀:

標準 Bot 資料契約 — 輸入 / 輸出 / 執行流程

crypto_trading（cyqnt_trd）· 本頁所有數值與 JSON 皆為實跑捕捉,非手寫範例
範例策略 mtf_trend_follow BTCUSDT 4h · 539 根 619 passed, 1 skipped, 12 warnings in 22.26s
一句話:策略只寫一個函式 make_signals(df),框架負責餵資料(DataSnapshot)與包訊號(SignalEnvelope)。 但輸出有三種形態,而真正上線的 live 路徑用的是第三種(trades.jsonl)—— 不是規格文件定義的那一種。

1. 輸入 — 資料怎麼進來

1.1 標準輸入物件:DataSnapshot

cyqnt_trd/standard_bot/core/contracts.py:227。 匯入:from cyqnt_trd.standard_bot.core import DataSnapshot(不在 cyqnt_trd 頂層)。

typed 欄位內容誰讀
marketMarketBundle — K 線,key = "BTCUSDT|4h"交易型
universeUniverseBundle — 24h ticker + Square ticker_rank + 候選 K 線選幣型
socialSocialFeedBundle — 新聞文件流選配
onchainOnChainSignalBundle尚未使用
metaSnapshotMeta — snapshot_id / decision_as_of / source_statusPIT 依據
衍生品沒有型別契約:funding_rate / open_interest / long_short_ratio / taker_cvd / liquidation 都不是 typed 欄位,而是塞在 Bar.extras: Dict[str, Any], 再由 bars_to_df 溢出成 df 欄。對 K 線做到了標準化,對衍生品只是「有地方放」。

1.2 統一 snapshot(交易型 + 選幣型合一)

過去 market 與 universe 只是型別上共存: assemble_snapshot() 沒有 universe 參數、 HistoricalSnapshotAssembler 只填 market、 build_selection_snapshot 只填 universe —— 沒有任何組裝器會同時填兩者。新增的 build_unified_snapshot()(standard_bot/data/unified_snapshot.py)補上這條路:

from cyqnt_trd.standard_bot.data import build_unified_snapshot

snap = build_unified_snapshot(
    market_bundle=bundle,        # 交易型的逐根資料
    universe_bundle=ub,          # 選幣型的橫斷面資料
    primary_timeframe="4h",
    fold_universe_klines=False,  # True = 把候選 K 線折進標準 market 路徑
    strict_pit=True,             # PIT 護欄
)

實跑結果 — 同一個 snapshot 同時驅動兩種 plugin:

snapshot_id    = 3d275257-5b59-52e8-9687-37d227927b86
decision_as_of = 1776311999999
market   有 → 539 根 Bar
universe 有 → as_of=1776311999999

交易型 plugin (mtf_trend_follow)      → trade signals = 1, side=sell
選幣型 plugin (news_catalyst_selector) → candidates = 3, first=BTCUSDT

並且會擋下 PIT 違規(universe 的 as_of 比最後一根確認 K 還新 = lookahead):

universe.as_of (1776321999999) is AFTER decision_as_of (1776311999999): the cross-sectional ranking was built from data the bars have not reached yet, which is lookahead. Rebuild the UniverseBundle with as_of_ms=1776311999999, or pass strict_pit=False to override.

2. 策略 — 你要寫的東西

範例 = strategies/technical/mtf_trend_follow.py(SOP 的參考模板)。核心只有一個函式:

def make_signals(df) -> tuple[pd.Series, pd.Series]:
    c, ef, es, et, adx, _atr = _factors(df, CONFIG)   # 全部走 canonical blocks
    cross_up = (ef > es) & (ef.shift(1) <= es.shift(1))
    trend_up, trend_dn = c > et, c < et
    strong = adx > CONFIG["adx_min"]
    long  = (cross_up & trend_up & strong).fillna(False)
    short = (cross_dn & trend_dn & strong).fillna(False)
    return long, short          # 兩條對齊 df index 的布林 Series

strategy.register(
    BOT_ID, make_signals,
    exit_cfg={"type": "atr_stop_tp", "atr_period": 14,
              "stop_mult": 2.0, "tp_mult": 3.0},
    size=0.1,
)

指標一律用 canonical blocks.indicators —— 三條路(回測 / paper / live)才會算出同一個值。

--tail-bars 陷阱(這支策略就會中):事件驅動引擎每根都在「最後 --tail-bars 根」的視窗上重算指標。本策略用 EMA200,而 CLI 預設是 120 → 指標全 NaN、0 交易且不報錯。實測:--tail-bars 120 → trades=0; --tail-bars 600 → trades=1。請設為 ≥ 最長週期的 2–3 倍 (現在 0 訊號時會印警告)。

3.3 輸出 C:trades.jsonl(live executor 真正吃的)

paper daemon 每產生一筆成交就 append 一行到 <state_dir>/trades.jsonl, mvp_live_executor 輪詢該檔、讀 action 去下真實單。 來源 = PaperFill(simulation/live_paper_session.py:40)。

{
 "fill_id": "3f2a…",
 "timestamp_ms": 1773993600000,
 "side": "sell",
 "price": 70811.9,
 "quantity": 0.01412,
 "fee": 0.4,
 "action": "open_short",
 "signal_bar_timestamp_ms": 1773993599999
}
三個必須知道的限制
  • 沒有 stop_loss / take_profit(欄位就這 8 個)→ 交易所端不會有掛好的保護單。停損是在 daemon 進程內模擬判斷、觸發時才送市價單; daemon 掉了,部位就沒有保護。
  • 它是成交記錄(fill),不是訊號(signal)。跟 §3.2 是兩個不同 schema,沒有欄位對應。
  • daemon 的出場一律排到下一根 open 市價成交,不像兩個回測引擎在停損價成交 → 回測會高估停損品質。

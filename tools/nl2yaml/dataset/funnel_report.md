## 0. Read this before using any number below

`capability.plan_conversion` needs conditions in its own vocabulary, and producing those is A1's job (an LLM). This pass substitutes a hand-written map from the miner's regex `(family, subject)` pairs onto capability subjects, so **every number here is an UPPER BOUND**. The true yield is strictly lower, for four reasons that all push the same way:

1. **Miner recall is a floor.** The regexes find a subset of a request's conditions. A row scored "all expressible" can still contain an unmined `not_expressible` one - which is exactly the 'exclude tradfi' accident: the blocking condition was in the text and not in the machine's hands.
2. **The map is coarse in the generous direction.** `volume` (a COIN count) is scored against `quoteVolume` (quote currency); `exclude` (the verb) is scored as `symbol_blacklist` without knowing *what* is excluded, because every plausible target happens to be expressible.
3. **`unknown` is forgiven in the headline.** 4231 rows / 2410 groups are "upper bound" only because a `(subject, scope, operator)` the table does not rule on was treated as expressible. The `strict` column removes them; section 5 lists exactly which keys they are.
4. **Scope is guessed for ambiguous rows.** `classify_request` returns ambiguous for 32748 rows. Those are scored in both frames and the better result kept - upward again.

A fifth, separate discount: expressible is not gradeable. See section 7.

Two things push the other way and are stated so they can be argued with:

* **The gap ranking is blind to 11 of the table's 16 gap ids** (section 5). Requests that hit an undetectable gap are scored as clean, so refusal-gold counts are floors.
* **Two intervals in one conversation are scored as a resonance request.** The miner reads the whole excerpt, so "look at 1h ... now 4h" is indistinguishable from "aligned on 1h AND 4h", and only the second needs the missing capability. That pushes rows OUT of the upper bound, which is the wrong direction, so the size of the effect is stated rather than argued: 18 selection / 626 trade rows (16 / 447 groups) are blocked by nothing else and would flip back into the bound if the heuristic is judged wrong.

## 7. Is this enough to fine-tune? (500-5,000 structured outputs)

The two dialects are separate tasks with separate grammars (`selection:` ranks a universe and emits candidates; `signals:` emits per-bar entries for one declared symbol). `validate_spec` refuses a spec that is both, so a mixed training set teaches a shape that cannot exist. Counted apart:

| dialect | scored rows | upper bound rows | **upper bound, deduped (groups)** | + >=1 expressible (groups) | minus overstated (groups) | strict (groups) | + user stated every number (groups) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| selection | 1718 | 520 | **395** | 340 | 395 | 298 | 286 |
| trade | 12304 | 9827 | **6699** | 6599 | 5802 | 5581 | 3526 |

The last column adds "and the user stated every number the spec needs" (families ['risk', 'rank_topn'] must carry a value). It is not a nicety: an expressible-but-unquantified `add a stop-loss` forces the annotator to pick the percentage, and a gold spec whose stop was invented by the annotator trains the model to invent stops. 15466 of the corpus's risk conditions carry no value at all.

`both` (2363 rows) and `unclear` (31955 rows) are excluded from this table on purpose: `both` is refusal gold, and `unclear` has no decided shape, so its target dialect would be the annotator's guess.

Refusal gold is a third, cheaper class and it is abundant:

| dialect | refusal gold rows | deduped (groups) |
| --- | --- | --- |
| selection | 563 | 422 |
| trade | 1231 | 866 |
| both | 2363 | 1471 |
| unclear | 1046 | 721 |

A refusal is not a consolation prize. It is the output that stops the accident this dataset exists because of: the gap vocabulary is closed, so a refusal is graded by string equality against an id known before generation, and grading it costs nothing and cannot drift. Both dialects need one.

### The answer

**Trade dialect: yes, with room to spare - the problem there is selection pressure, not scarcity.** 6699 distinct requests clear the bound, 5581 survive the strict reading, and 3526 also have every number the user stated rather than an annotator's guess. The band is 500-5,000; the tightest of those columns is already inside it, so the trade set can be cut for quality (quantified, tier A/B, one row per split group) instead of scraped for volume, and a genuine held-out test set is affordable.

**Selection dialect: no, not as spec emission.** 395 distinct requests clear the bound - and that is the ceiling, before A1's own error rate and before a human rejects the ones the miner scored generously. Realistically that lands well under 300, against a floor of 500. Adding the refusals gets the selection *task* to 817 distinct targets (395 specs + 422 refusals), which does clear 500, but half of that set teaches the model to decline. Train that head, and do not claim a selection spec generator on 395 examples.

Three ways to close the selection shortfall, in order of leverage. All three are worth more than more chat data, because the corpus is not short of selection *requests* - it is short of selection requests this repo can answer:

1. **Decide the shape of the ambiguous rows.** `classify_request` returns `ambiguous` for 32748 of 51595 rows, and that bucket holds 5527 upper-bound distinct requests with no dialect assigned - more than the trade dialect yields in total. Only 2232 rows in the whole corpus are classified `selection` at base. Sharpening the classifier (or letting A1 decide the shape and recording its choice as a field) is a cheaper move than any block, and it is where the selection examples are hiding.
2. **Close `GAP-PER-SYMBOL-INDICATOR` (`universe.augment_with_indicator`).** 1264 distinct requests are blocked by it and 784 are blocked by nothing else, so closing it alone converts them. "Scan the market, then run the indicator on each survivor" is the shape the selection dialect is missing, and it is the same gap the Supertrend accident came from.
3. **Decide what a compound request should produce.** 1471 distinct requests (2363 rows) ask for a screen AND per-bar execution, and today all of them are refusals - that bucket alone is 3.7x the entire selection spec yield. They do not need a new block so much as a decision: two specs, or a declared refusal. Either answer converts them into training targets; leaving it undecided keeps the largest single block of selection-flavoured demand in the corpus unusable.

**One practical note on cost.** A1 does not need 51595 calls. Conditions are computed per unique canonical text and cases split by group, so one pass over the 16472 candidate split groups covers the 26161 candidate rows - a 1.6x saving - and it is also the only way the train/test split stays honest.

**And one warning about what this pass cannot tell you.** Section 5 sees 5 of 16 gaps and the miner's recall is a floor, so the refusal counts above are floors and the spec counts are ceilings. The number that would settle it is the one this pass deliberately did not spend: run A1 over a stratified sample of a few hundred split groups, have a human adjudicate every condition, and compare the realised level-5 rate against the 80% and 30% upper bounds in the shape table. Until then, treat the trade 'yes' as firm and the selection 'no' as firm, and treat everything between them as unmeasured.
